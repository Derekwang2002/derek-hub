# Article Benchmark

把有解释价值的量化对比放在论点附近，让读者能切换指标，并看清数值依据。只在 **derek-hub** 使用本 Skill；不安装到用户级目录，不向其他项目添加调用规则。

## 先判断是否适合

在当前文章任务中主动判断，无需等用户说出 Skill 名称，但不要顺带改写其他文章。

适合：同一条件下不同方案的对比、优化前后对比、同一组方案的多个指标，或能写出推导过程的教学模型。通常少量方案、两三个指标最容易阅读；数量由内容决定。

这次接入的用途可作为判断参考：

| 段落问题 | 合适的图表内容 | 数据边界 |
|---|---|---|
| Ponytail 到底减少了什么？ | 代码量、成本、耗时分别切换 | 引用固定版本实验；不能说成单独运行 review 的效果 |
| BuildKit 为什么能少做工作？ | 首次构建、修改源码、修改依赖时的 RUN 次数 | 根据明确的 Dockerfile 顺序推导；次数不等于耗时 |
| 覆盖索引省掉了哪一步？ | 扫描记录与回表次数 | 给定数据量和查询条件；不捏造毫秒数 |
| CALL-E 哪段等待可以减少？ | 版本复用、并行依赖、结果回传的预算 | 明确假设和计算；不当作系统实测或 P95 |

单个数字、两句话就能解释的小差异，用正文或表格。依赖关系用流程图；随时间变化用折线图；混合单位、负数、分布或不确定区间，不硬塞进当前条形图。如果用户只问“哪里适合用”，先给具体位置和数据缺口，不直接修改文章。

## 读取现有实现与周围页面

以下路径均相对仓库根目录。先读当前文件，既有实现是唯一代码来源，不在 Skill 中维护副本：

- `src/components/benchmark-card.tsx` 与 `benchmark-card.module.css`：交互、条形图和正文紧凑样式。
- `src/components/gradient-showcase.tsx` 与 `gradient-showcase.module.css`：可选的视觉外框。
- `lib/benchmark.ts`：数据类型与校验规则。
- `src/components/markdown-renderer.tsx`：`benchmark` fenced block 的解析入口。
- 目标文章、对应英文稿，以及目标页面使用的正文容器和设计变量。

新增文章图表时，先阅读 [接入格式与项目验证](references/integration.md)。复用现有入口；不要为每篇文章加独立图表组件、硬编码路由分支或复制 `mock-benchmark.html`。

## 确定数值口径

- 已发表实验核实原始来源，保留可追溯的链接、版本或日期、工作负载及必要实验条件。没有重新核实时，不把历史快照描述成最新结果。
- 解释型教学任务可以使用明确的假设和公式，并在图表附近标注“教学模型 · 非实测”。缺少真实数据时，不以虚构结果满足用户要求的实测 benchmark；先寻找已有记录，确实缺少再说明需要什么。
- 同一标签页只比较同一指标、同一单位、兼容条件的数据；说明越高还是越低越好。不同指标分标签展示。
- 相对指数须写明基线。例如减少 54% 对应基线 100、剩余约 46；不要把减少比例 54 画成剩余值。不能把减少的代码量解释为正确性提升。
- 条形从零起算，零值必须为空条。不得为了可见性强制最小宽度而歪曲比例。当前各标签页按各自最大值缩放，跨标签页不能直接比较条长；需要共同尺度时先扩展组件。
- 每个图表都有标题、可见的数据性质和方法说明。只把来源写进 JSON 注释、代码注释或 hover 提示不算完成。

## 必做：适配周围 UI

先查看目标段落及相邻标题、正文、代码块或图片，确认文章宽度、字体、字号、颜色变量、段落节奏与明暗主题。已有页面以实际渲染为准；新文章参考同类页面。

- **位置与密度**：放在它支撑的论点之后、下一节之前，通常一个清晰标题加一句引导即可。使用现有 `.inline` 正文样式，避免带入 mock 的最小高度、大面积空白和展示页尺寸；说明文字需可读，不能为了装饰压缩绘图区。
- **视觉层级**：正文列宽、字体和文章节奏优先。标题、注释和 badge 使用项目变量（例如 `--color-text-muted`），不要假设不存在的 CSS token。条形高亮服务于对比，不把每个方案都强调。
- **外框与主题**：渐变和深色面板是可调整的外观，不是强制模板。在浅色页检查深色嵌入块是否协调；必要时用局部 variant 降低渐变、阴影、圆角或改用页面 surface 颜色。保留已经协调的外观，不为单篇文章全局重设所有卡片。
- **局部作用域**：通过现有 CSS Module、className 或小型 variant 调整。不同文章的需求不一致时保持默认兼容；不改全局 `button`、`figure`、`p` 或整个站点主题来迁就这张图。
- **窄屏与长文案**：在真实正文容器中检查窄屏。标签可在组件内横向滚动，但不显示滚动条；同时设置横向滚动和纵向隐藏，选中下划线不得越界产生纵向溢出。页面本身不应新增横向溢出。英文长标签、中文换行、数值与单位均不得裁切；不缩小到难以阅读，也不禁止用户缩放。
- **交互与无障碍**：保留实例级唯一 ID、tab/panel 关联、选中状态、不带修饰键的方向键及 Home/End 导航、可见焦点和 reduced-motion。遇到 Meta/Command、Ctrl、Alt 或 Shift 组合键时直接交还浏览器，不切换标签、不调用 preventDefault，避免抢占后退/前进等快捷键。切换后数值、说明、主题对应当前标签；不用颜色或动画单独传递结论。

## 接入与验收

1. 只改当前任务需要的正文、英文对应段落和必要组件。用合法 JSON 的 `benchmark` fenced block 接入；不要修改原文章日期、slug 或所属栏目。
2. 中英文保持场景 ID、数值、单位含义和证据性质一致；翻译标题、标签、说明与辅助文本。代码、公式和来源链接按原含义保留。
3. 用解析器校验数据，再运行与变化相关的现有测试和类型检查；修改渲染路径或交互时进行生产构建。不要为了补图重写无关功能。
4. 查看生成 HTML 和实际文章：不能留下可见 JSON 代码块。验证每个标签页的内容、键盘操作、零值、来源链接、桌面与窄屏；涉及主题样式时检查明暗两种状态。多实例不得重复 DOM ID。
5. 检查改动是否影响目录、语言切换及项目 pager 的实际 href。保留用户其他修改，区分已有检查问题和本次问题。
6. 交付具体文章位置、数据性质、验证结果与本地/部署状态。加图不自动授权提交、推送或部署。
