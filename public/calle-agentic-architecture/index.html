CALL-E agentic
component architecture.

The runtime is a stack of composable layers. Each layer owns a few components; each component lists what it does today and the extension points you build new capabilities on — a new tool, a new goal_type, a new call provider, a new skill. The request flow is kept below only as a reference.

User→ MainAgentcommit_goal→ Dispatcher→ Goal Agentcreate_voice_run→ VoiceRunExecutor→ Wake Scheduler
report: projection + summary → MainAgent → user terminal call event → re-dispatch next_wakeup_at due → re-dispatch · daily/weekly follow-up · planned

持续跟进 · continuous follow-up batch · progressive

The goal is done only when the user's real-world objective is met — e.g. a 银行催收 debtor actually repays — not when a call ends. So the agent re-dispatches on a cadence via the Wake Scheduler until then.

call → objective met? → ✗ wait · daily / weekly ↺ via Wake Scheduler | ✓ goal done

Inbound · one pipeline, a new branch

Reuses the same dispatcher, goal-event log & report contract as outbound — it's a new goal_type, not a new pipeline. Simulate (03) & Report (08) draw on the Knowledge layer; the operate loop (07–10) is the same Scheduler cadence.

Planned — no inbound goal_type in code yet.

03

One-shot call · runtime sequence

live · the only path built today

The concrete trace of a single one_shot_outbound goal — from the user's request to a resolved objective. Two dispatch iterations bracket one real call: iteration ① plans the RunSpec and queues the call; the call runs detached; its terminal event re-dispatches iteration ② to evaluate the outcome and report back to the user. Each dispatch is one OutboundGoalAgent turn that must end in complete_goal_iteration.

sync call / return async · event key business tool report → user ⟳ self-action ▭ dispatch iteration
