理解分层架构时，很容易记住这样一句话：容易变化的层，应该依赖不容易变化的层。

课程报名的例子似乎刚好符合这个解释：API 和 DB 放在外侧，service 编排流程，domain 保存核心规则。外侧可能换框架、换数据库，内侧的报名规则相对稳定。

但真正做产品时，情况经常相反。数据库和 Web 框架几年没换，产品却每周调整资格、价格和流程。domain 和 service 可能恰好是修改最频繁的部分。

这时，依赖方向需要反过来吗？如果不需要，分层到底在保护什么？小项目值得为此增加那么多文件和接口吗？

我的理解是：**分层的价值在于按变化原因划分职责，用明确的契约限制变化的传播。修改频率只是观察信号，不能单独决定依赖方向。**

本文从 B 站[《5 分钟学会架构设计》](https://www.bilibili.com/video/BV1CXet6gE6X/)的报名案例总结笔记出发，再结合 Clean Architecture、六边形架构和 Transaction Script，讨论这些问题。关于适用规模和取舍的部分，是在案例基础上的进一步分析。

## 从一个报名函数拆出四种职责

最直接的报名实现，通常把几件事写在一起：解析请求、查询学生和课程、检查是否重复报名和满员、保存结果，最后返回 HTTP 响应。

代码能够运行，但理解和验证一条规则，需要同时面对业务条件、SQL、连接和 HTTP 异常。一个函数承担了多种变化原因。

把它拆开后，各部分回答不同的问题：

| 部分 | 核心问题 | 报名例子 |
|---|---|---|
| domain | 业务上哪些行为合法？ | 不允许重复报名，不允许超过容量 |
| service | 完成一个用例需要安排哪些步骤？ | 获取数据、执行报名规则、保存结果 |
| API | 外部如何发起操作、理解结果？ | 解析参数，把业务结果转换成 HTTP 响应 |
| DB 实现 | 数据具体如何读取和持久化？ | SQL、ORM、字段映射和存储操作 |

这里的 service 指应用用例编排，也不等于独立部署的微服务。domain 可以使用带行为的对象，也可以使用数据结构和普通函数。把报名行为放进 `Course` 对象是一种建模选择，并非必须遵守的形式。

四层也不是四个必选文件夹。Clean Architecture 的原始说明明确指出，层数是示意；真正重要的是职责和源代码依赖的组织方式。[参考：The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)

## “稳定”至少有三种含义

讨论谁应该依赖谁之前，需要先区分三个问题。

**实现是否经常修改？** 这是版本记录中能够观察到的代码变化频率。

**对外契约是否经常修改？** 调用者需要知道的参数、结果、错误、行为保证，是否经常变化？契约不只是一段函数签名，也包括失败方式和调用约束。

**是否容易受到其他变化影响？** 报名资格会随产品决策变化，但不应该因为 HTTP 框架升级而变化。

这三个维度并不相同。一个模块可以每周修改内部规则，却保持对外契约稳定；也可以一年没改，却因为暴露了大量内部细节，让调用者与它紧密绑定。

因此，“业务规则稳定”更适合理解为：业务规则应当尽量不受无关技术变化影响。它不意味着业务规则在时间上永远不变。

反过来，数据库产品多年不换，也不等于存储代码不变。查询、表结构、索引和事务处理可能持续调整；API 使用的框架不换，也不代表对外契约没有变化。

按 Git 提交次数给四层排序，再据此决定依赖方向，会混淆这些不同的变化。

## 依赖倒置改变的是代码依赖

service 要读取课程，自然需要在运行时调用存储操作。依赖倒置并没有取消这次调用。

它改变的是：service 在写代码时，需要认识谁。

直接依赖具体实现时，service 必须知道某个 PostgreSQL 存储类。引入业务侧定义的存储接口后，service 只需要知道“能够读取课程、保存报名结果”，具体实现由外部提供。

```text
Source dependencies:

API adapter ----------> EnrollmentService ------> Domain
                               |
                               v
                      EnrollmentStore interface
                               ^
                               |
                     PostgreSQL adapter

Runtime call:
EnrollmentService -> injected store object -> database
```

图中向上的箭头表示 PostgreSQL adapter 实现业务侧定义的接口，不表示数据库在运行时主动调用 service。将这层关系简写成“DB 依赖 service”，容易让人混淆源代码依赖与执行顺序。

依赖注入则负责组装：创建存储对象，把它传给 service，再让 API 使用这个 service。普通的构造函数参数或函数参数就能完成，不一定需要依赖注入容器。

接口也不是越通用越好。若一个所谓的存储接口仍要求调用者传 SQL、理解 ORM session 和数据库行对象，业务代码仍然需要掌握存储细节。接口的价值取决于它实际隐藏了多少调用者不必知道的复杂性。

## domain 变化最快时，架构仍然可能有效

假设报名用例对外提供这样的操作：

```text
enroll(student_id, course_id) -> EnrollmentResult
```

产品现在把“开课前允许报名”改成“开课前 24 小时截止”。如果已有数据包含开课时间，已有失败结果也足以表达拒绝，那么这次变化可能只需要修改资格判断和对应测试。

service 继续获取数据、调用规则、保存结果；API 继续接收两个 ID；存储继续读取相同信息。

**domain 发生变化，并不等于所有依赖它的代码都必须修改。** 内部实现变化与对外契约变化，是两件不同的事。

业务规则越频繁变化，把它们集中表达、独立验证就越可能有收益。修改截止时间时，维护者能够只关注时间条件，不必同时理解 HTTP 请求和数据库连接。

六边形架构的重要动机之一，就是让应用能够脱离具体 UI 和数据库进行测试，并由用户操作、程序或批处理等不同入口驱动。[参考：Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture)

不过，如果产品把“立即报名成功”改成“先付款，再审核，最后确认”，情况就不同了。新的业务语义可能同时要求：

- domain 增加待付款、待审核等状态及转换规则。
- service 编排付款和审核流程。
- DB 保存新增状态和记录。
- API 暴露相应操作，返回新的结果。

这种联动来自需求本身。合理的架构可以让各部分承担清楚的职责，却不能消除业务语义变化带来的必然修改。

评价解耦时，更有用的问题是：这次跨模块修改是需求必然要求的，还是因为实现细节泄露造成的？

### 将经常变化的规则收拢到更小的范围

如果报名流程相对固定，但普通课程、会员课程和活动课程的资格判断不同，可以先把资格判断提取成一个独立函数。流程只需要知道是否允许，以及拒绝原因。

当真正出现多套规则需要切换或独立维护时，再考虑策略接口。只有一个简单条件时，一个清晰的函数通常已经足够。

如果所有规则都可能随产品探索被推翻，就应保持模型简单，允许重构。过早建立通用规则引擎，容易把尚未理解的变化固化成一个更难修改的框架。

API 和 DB 长期稳定也完全正常。分层仍然可以靠降低测试和修改成本获得价值；如果这些收益都不存在，就没有必要为了“将来可能换数据库”建立完整的隔离体系。

## 需要多大的业务，才值得这样拆分？

用户数、QPS 和代码行数，都不是可靠的单一门槛。

一个访问量很大的简单查询服务，业务逻辑可能很薄；一个只有几百名用户的结算系统，因为金额、审批和状态规则复杂，反而值得认真建模。流量主要提出容量和性能问题，职责划分主要处理理解、修改和协作问题，两者不能直接换算。

我更关注这些已经出现的信号：

| 已有问题 | 值得考虑的拆分 |
|---|---|
| 同一规则在 HTTP、定时任务和导入脚本中重复 | 将共同业务能力集中到可复用的用例或规则模块 |
| 验证一个计算或资格判断必须启动整套服务 | 分离纯规则与外部交互 |
| 改一个条件要同时理解请求、ORM 和 SQL | 收拢规则，缩小维护者需要掌握的范围 |
| 相同状态和金额规则散落多处，修改经常遗漏 | 明确规则的唯一维护位置 |
| 一次需求经常触发无关模块返工 | 检查共享数据结构和实现细节是否泄露 |

业务复杂度、变化引发的连锁影响、团队协作和预期维护周期，通常比“到了多少万用户”更能说明问题。

也不必要求所有业务采用相同的结构。复杂的报名流程可以有独立规则和存储接口；旁边一个只读列表可能直接通过查询返回数据。每个模块承担的复杂度不同，所需结构也可以不同。

## 收益与代价，都发生在日常维护中

分层最常见的收益，是减少完成一次修改需要理解和验证的内容。

- **修改集中。** 调整报名资格时，规则有明确位置，不必寻找多个副本。
- **测试直接。** 给规则提供输入，验证结果，减少环境准备。
- **能力复用。** 网页、后台任务和批量导入可以使用同一套业务行为。
- **协作清楚。** 模块之间通过明确契约交互，降低对内部实现的共同依赖。

对应的代价则是更多接口、数据转换、对象组装和文件跳转。多种模型需要保持一致，团队需要共同理解契约。抽象设计错了，还可能导致一个简单字段要贯穿五层修改。

最典型的警示信号，是每层只做参数转发：

```text
Controller -> Service -> Repository -> ORM
```

这条调用链本身不能证明设计有问题。关键在于每一层是否承担规则、转换或约束，以及是否隐藏了复杂性。如果每层暴露的信息几乎一样，维护者仍需一路读到底，新增结构的收益就很有限。

可以做一个“删除测试”：假设去掉某个模块，它处理的复杂性会重新散落到多个调用者中吗？如果会，这个模块在承担价值；如果复杂性随它一起消失，它可能只是多余的转发。

从经济角度看，可以用一个粗略的判断框架：

```text
Expected benefit:
recurring changes × effort saved per change
+ reduced regression and coordination cost

Expected cost:
initial extraction + ongoing interface and mapping maintenance
```

这不是可以精确计算的公式，也不存在通用的收益百分比。它提醒我们检查实际变化：最近几次需求能否更快定位、更少重复修改、更容易验证？

## 报名案例还隐藏着两个现实成本

### 换数据库不只是修改一行组装代码

“在组装处换一个实现”成立的前提，是新实现已经完成，而且满足原有契约。

真正从 SQLite 迁到 PostgreSQL，还可能涉及 SQL 方言、数据迁移、事务隔离和性能验证。接口能降低业务代码与具体实现的耦合，却不能替代迁移工作。

因此，数据库可替换性通常更适合作为架构带来的额外能力。是否值得抽象，仍要看当前的测试、维护和复用需求。

### 规则正确，不代表并发下仍然正确

假设课程只剩一个名额，两个请求同时读取课程，两次 domain 检查都可能认为“还有空位”，随后都保存成功。

内存中的容量判断表达了业务意图，却没有独自保证并发一致性。具体方案可能需要事务中的锁、带版本检查的更新，或将容量条件纳入原子写入；重复报名还可以通过适当的唯一约束防止。

这些机制需要协同设计：用例决定一次操作需要什么原子性，存储实现提供相应保证，失败结果再回到业务流程中处理。一个简单的 `get` 加 `save` 接口，如果没有说明一致性契约，就可能隐藏了最重要的问题。

因此，纯规则测试、存储集成测试和必要的并发测试各有职责。内存中的替身不能证明真实数据库的事务行为正确。

## 从小项目开始，逐步增加结构

我更倾向于随着问题出现，逐步增加结构。

**第一步：先写清楚一个用例。** 路由处理 HTTP，业务函数表达操作步骤，必要时直接使用 ORM。对于简单 CRUD，不必给每张表都配齐 domain、service 和 repository。

这种以一个过程处理一次业务请求、将公共步骤提取为子过程的组织方式，对应 Fowler 描述的 Transaction Script。它本身就是一种正式的业务逻辑组织模式。[参考：Transaction Script](https://martinfowler.com/eaaCatalog/transactionScript.html)

**第二步：提取已经复杂的规则。** 将计算、资格判断和状态转换集中表达，使其容易独立测试。可以先用函数，等对象确实有需要共同维护的数据和行为时，再引入更丰富的模型。

**第三步：为现实中的替换需求建立接口。** 如果真实数据库妨碍规则测试，或者支付、通知已经存在不同实现，再在相应位置引入小接口。测试替身也可以是一个现实的替换需求，但仍需保留真实实现的集成验证。

**第四步：业务增长后，按业务模块组织。** 报名、支付、课程各自维护自己的能力，每个模块内部采用合适的分层程度，避免形成所有功能都往里堆的巨大 service。

这些步骤都可以发生在一个应用、一个进程中。拆模块与拆微服务需要解决的问题不同；独立部署带来的网络、运维和一致性成本，应当另行评估。

## 让每一层说明自己减少了什么成本

回到最开始的疑问：domain 和 service 变化最快，并不直接否定分层。它反而要求我们更认真地判断，哪些变化能够通过稳定契约被限制在模块内部，哪些变化确实会改变整个业务流程。

我会把这次学习浓缩成三个判断：

- 依赖应面向明确的业务能力和契约，不能仅按代码修改频率排序。
- 分层是否有效，要看它是否让常见修改更集中、规则更容易验证、调用者需要了解的细节更少。
- 拆分到什么程度，由实际复杂度和维护收益决定；每一层都需要承担足以抵偿其存在成本的职责。

对一个具体项目，最有用的追问是：增加这个模块后，下一次常见需求会在哪里修改，需要理解多少内容，又怎样确认没有改坏？
