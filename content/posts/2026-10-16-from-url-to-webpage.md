在浏览器里输入一个网址，按下回车，页面就出现了。这个过程中，浏览器需要找到服务器、建立连接、请求文件，还要把收到的 HTML、CSS 和图片转换成屏幕上的内容。

初学计算机网络时，DNS、TCP、IP 往往分在不同章节。单独看定义不难，放在一起就容易混淆：已经有 IP，为什么还需要 MAC？DNS 查询自己又是怎么发出去的？TCP 建立连接后，为什么还要进行 TLS 握手？

这篇文章用一个商品页把这些问题连起来。必要的术语会在第一次出现时解释，后面附上一张完整时序图。最后再补上带宽、滑动窗口和路由等背景，方便回头理解每一层在做什么。

## 先确定这次访问的环境

我们输入的 URL 是：

```text
https://shop.example.com/products/42?color=blue#reviews
```

页面里有蓝色机械键盘的名称、价格、图片和评论区。假设电脑通过网线连接家用路由器，使用 IPv4，网站采用 HTTP/2 和 TLS 1.3。这次没有可用的 DNS、网页缓存，也没有现成连接；DNS 查询采用普通 UDP。这是一条便于跟踪的访问路径，实际浏览器可能使用缓存、加密 DNS、IPv6 或 HTTP/3。

| 角色 | 示例地址 |
|---|---|
| 电脑 | `192.168.1.10/24` |
| 家用路由器的内网接口，也就是默认网关 | `192.168.1.1` |
| 家用路由器的公网接口 | `198.51.100.23` |
| DNS 递归解析器 | `192.0.2.53` |
| 网站服务器，稍后通过 DNS 查到 | `203.0.113.80` |

域名和公网地址都用于教学，不代表实际部署。路由器的内网接口连接家庭网络，公网接口连接运营商网络；它们是不同的网络接口。

先分清三种标识：IP 地址用于网络层寻址；MAC 地址用于本地链路上的帧交付；端口用于区分主机上的通信端点。例如 `203.0.113.80:443` 表示目标 IP 和 HTTPS 常用端口。一个服务器端口可以同时服务很多连接。

## 分层：同一份数据，经过不同处理

网络分层把通信拆成几类工作。本文采用五层教学模型：

| 层 | 负责什么 | 本文涉及的协议或技术 |
|---|---|---|
| 应用层 | 定义应用交换的信息 | DHCP、DNS、HTTP |
| 传输层 | 在应用端点之间传送数据 | TCP、UDP |
| 网络层 | 让分组跨网络转发 | IP |
| 数据链路层 | 在当前链路上传送帧 | 以太网、ARP |
| 物理层 | 把比特编码成信号 | 网线中的电信号、光纤中的光信号等 |

“分组”是网络层处理的数据单位，“帧”是链路层处理的数据单位。发送方给数据加上各层需要的信息，这叫封装；接收方按相反方向处理，叫解封装。以未加密的 HTTP over TCP 为例：

```text
应用层：                    HTTP 数据
传输层：           TCP 头 + HTTP 数据
网络层：    IP 头 + TCP 头 + HTTP 数据
链路层：帧头 + IP 头 + TCP 头 + HTTP 数据 + 帧尾
物理层：把这些比特编码为信号发送
```

HTTPS 还要经过 TLS，加密发生在 HTTP 数据进入 TCP 字节流之前。TLS 在这里位于应用协议和 TCP 之间，不必强行给它分配一个固定的 OSI 层号。

OSI 模型分七层，额外区分表示层和会话层；TCP/IP 常见四层模型则把底部合称链路层。这些模型的划分不同，讨论具体协议时先说清采用哪种模型即可。

## 入网时，DHCP 已经给电脑提供了配置

在打开网页之前，电脑通常已经获得自己的 IP、子网掩码、默认网关和 DNS 服务器地址。这个过程可以由 DHCP 自动完成。家用路由器经常同时提供 DHCP 服务：

```text
电脑                         DHCP 服务器
 │── Discover：寻找服务器 ─────→│
 │←─ Offer：提供配置 ───────────│
 │── Request：请求选定配置 ─────→│
 │←─ ACK：确认分配 ─────────────│
```

这四步常简称 DORA。DHCP 使用 UDP，客户端端口是 68，服务器端口是 67。最初没有 IP 时，客户端可以用 `0.0.0.0` 作为源地址发出广播。分配的地址通常有租约，需要续租。

本例得到的配置是：

```text
IP：       192.168.1.10
子网掩码： 255.255.255.0，也写作 /24
默认网关： 192.168.1.1
DNS：      192.0.2.53
```

`/24` 表示地址的前 24 位是网络前缀。这里电脑所在子网是 `192.168.1.0/24`。访问不在这个子网中的目标时，通常要通过默认网关。

DHCP 发生在获取或更新网络配置时，不会随着每一次网页访问重新执行。

## 解析 URL，然后准备查 DNS

按下回车后，浏览器识别 URL 的各个部分：

| 部分 | 本例的值 | 含义 |
|---|---|---|
| 协议 | `https` | 使用 HTTPS |
| 主机名 | `shop.example.com` | 要访问的主机名称 |
| 端口 | 默认 `443` | 目标服务端口 |
| 路径 | `/products/42` | 请求的资源 |
| 查询参数 | `color=blue` | 提交给服务器的参数 |
| 片段标识 | `reviews` | 浏览器定位页面内的评论区 |

`#reviews` 不会作为 URL 的一部分发给服务器。服务器收到的路径和查询参数是 `/products/42?color=blue`；页面返回后，浏览器再处理片段标识。

浏览器还会检查能否使用缓存或已有连接。本例都没有，于是需要把 `shop.example.com` 解析成 IP。DNS 是完成名称解析的应用层协议，A 记录表示 IPv4 地址，AAAA 记录表示 IPv6 地址。

假设电脑准备向 DNS 解析器发送：

```text
UDP 源端点：192.168.1.10:53000
UDP 目的端点：192.0.2.53:53
查询内容：shop.example.com 的 A 记录
```

`53000` 是这次通信选择的临时端口，`53` 是 DNS 服务端口。问题随之出现：DNS 请求本身也要经过网络，电脑怎样把它发给外网解析器？

## ARP 先找到网关的 MAC

操作系统查路由表，发现 `192.0.2.53` 不在本地子网，选择下一跳 `192.168.1.1`。下一跳是当前需要把分组交给的设备；这个决定不改变分组的最终目的 IP。

以太网帧需要填写目的 MAC。假设电脑的 ARP 缓存中还没有网关记录，就广播询问：

```text
电脑 → 本地网络：谁的 IP 是 192.168.1.1？
网关 → 电脑：192.168.1.1 对应我的 MAC 地址 GL。
电脑缓存：192.168.1.1 → GL
```

ARP 用于本地 IPv4 地址与链路层地址的解析。ARP 报文直接放在以太网帧中，没有 TCP 或 UDP 端口。

接下来发出的 DNS 请求中，两层目的地址分别是：

```text
IP 目的地址： 192.0.2.53，也就是 DNS 服务器
帧目的 MAC：  GL，也就是本地网关
```

电脑不用知道远端 DNS 服务器的 MAC。远端链路的交付由那一段网络处理。这里也说明，不能把流程固定背成“先 DNS，再 ARP”：ARP 可能是把 DNS 请求发出去的前提。

## DNS 请求怎样抵达解析器

请求逐层封装：

```text
DNS 查询
   ↓
UDP：53000 → 53
   ↓
IPv4：192.168.1.10 → 192.0.2.53
   ↓
以太网：电脑 MAC → 网关 MAC
   ↓
物理层：通过网线发送信号
```

网关收到帧，取出 IP 分组，查表转发。由于电脑使用内网地址，本例还要经过 NAT，也就是网络地址转换。若同时转换端口，更准确地说是 NAPT。路由器为 DNS 通信记录一条映射：

```text
内部端点                         公网端点
192.168.1.10:53000    ↔    198.51.100.23:63000
```

DNS 解析器看到的源端点因此是 `198.51.100.23:63000`。回复到达路由器后，再按照映射转回电脑。NAT 的作用是转换地址与端口，不负责加密内容。

普通路由器根据目的 IP 查转发表，决定下一跳。每经过一个路由跳点，IPv4 的 TTL 都会减少，以免分组陷入转发循环；路由器也会为出链路重新封装。若出链路是以太网，目的 MAC 就是当前下一跳的 MAC。

同一局域网里的普通二层交换机通常只转发帧，不会像跨路由跳点那样改写源、目的 MAC。

解析器收到查询后，先检查自己的缓存。假设也没有答案，就依次查询：

```text
电脑
  │ 查询 shop.example.com
  ↓
递归解析器
  ├─ 根服务器 → 获得 .com 名称服务器线索
  ├─ .com 服务器 → 获得 example.com 权威服务器线索
  └─ example.com 权威服务器 → 返回 203.0.113.80
```

这些是解析器自己发起的新查询，使用它自己的网络端点。客户端要求解析器给出最终结果，解析器则沿转介逐步查询。最终答案返回电脑，并按 DNS TTL 缓存。这里的 TTL 是缓存时间，与 IP TTL 的含义不同。

DNS 名字本身也是分层的：

```text
shop.example.com.
             .  根
           com  顶级域
       example  下一级域
          shop  具体名称
```

DNS 还能保存 CNAME 别名、MX 邮件服务器、NS 权威服务器、TXT 文本等记录。反向解析常用 PTR；现代 SPF 邮件策略发布在 TXT 记录中。DNS 既可以使用 UDP，也可以使用 TCP；本文只是选择了一次普通 UDP 查询。

## TCP 建立连接，NAT 再记录一条映射

现在知道网站在 `203.0.113.80:443`。系统选择临时 TCP 端口 `51514`，准备建立连接：

```text
192.168.1.10:51514 → 203.0.113.80:443
```

TCP 是面向连接的传输协议，提供可靠、有序的双向字节流。连接是两端维护的状态，包括序号、窗口等信息，不是在沿途预留一根专用线路。UDP 则按独立报文发送，本身不提供 TCP 的重传和顺序保证。

先单独看三次握手：

![TCP 三次握手示意，客户端序号为 100，服务器序号为 500，双方依次确认对方的初始序号。](/blog/from-url-to-webpage/handshake-basics-zh.svg)

图 1：用较小的序号理解 SYN、SYN+ACK、ACK。[查看大图](/blog/from-url-to-webpage/handshake-basics-zh.svg) · [Mermaid 源文件](/blog/from-url-to-webpage/handshake-basics-zh.mmd)

SYN 占用一个序号，因此确认号要加 1。第三条消息让服务器知道，客户端已经收到了自己的连接建立信息。

回到商品页，路由器为 TCP 建立另一条 NAT 映射。它和前面的 UDP 查询不是同一个通信：

```text
电脑内网端点                     对外使用的端点
192.168.1.10:51514    ↔    198.51.100.23:62001
```

| 位置 | 源端点 | 目的端点 |
|---|---|---|
| 家庭网络内 | `192.168.1.10:51514` | `203.0.113.80:443` |
| 进入公网后 | `198.51.100.23:62001` | `203.0.113.80:443` |
| 响应在公网中 | `203.0.113.80:443` | `198.51.100.23:62001` |
| 响应回到家庭网络 | `203.0.113.80:443` | `192.168.1.10:51514` |

本例用下面这组序号展示握手，沿途网关和路由器先折叠起来：

![商品页 TCP 连接的三次握手，客户端初始序号 1000，服务器初始序号 8000，每条消息都通过底层网络传输。](/blog/from-url-to-webpage/handshake-example-zh.svg)

图 2：具体访问中的握手。每条箭头都经过 IP、链路层和物理层。[查看大图](/blog/from-url-to-webpage/handshake-example-zh.svg) · [Mermaid 源文件](/blog/from-url-to-webpage/handshake-example-zh.mmd)

TCP 连接建立后，服务器还没有向浏览器证明网站身份，网页内容也还没有获得 HTTPS 加密保护。这些由 TLS 完成。

## TLS 验证服务器身份，并协商通信密钥

TLS 是保护传输内容的协议。本例采用 TLS 1.3 的完整证书握手：

```text
浏览器                                      服务器
  │── ClientHello ───────────────────────────→│
  │   支持的算法、临时密钥交换信息等             │
  │←─ ServerHello ────────────────────────────│
  │←─ 加密扩展、证书、签名证明、Finished ───────│
  │                                           │
  │ 验证证书和握手消息                         │
  │── Finished ──────────────────────────────→│
  │←──────── 加密的应用数据 ──────────────────→│
```

浏览器检查证书是否适用于 `shop.example.com`，证书链能否连接到信任的根，以及有效期等条件。服务器还通过握手签名证明自己持有相应私钥。

双方利用临时密钥交换信息计算共享秘密，再派生通信密钥。后续网页内容使用对称加密与完整性保护。证书并不是用来把整份网页直接进行公钥加密的。

握手同时通过 ALPN 协商应用协议，本例选择 `h2`，即 HTTP/2。SNI 则用于在 TLS 握手中表明目标服务器名称。两者解决不同问题。

## HTTP 说明要哪个页面，服务器生成响应

HTTP 定义请求和响应的含义。完成 HTTP/2 初始化后，浏览器发出请求。下面是可读的字段示意，实际 HTTP/2 使用二进制帧传输：

```text
:method: GET
:scheme: https
:authority: shop.example.com
:path: /products/42?color=blue
accept: text/html
accept-encoding: gzip, br
```

GET 表示获取资源，路径指定 42 号商品，查询参数选择蓝色。服务器上的应用可能读取商品数据，再生成 HTML：

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <link rel="stylesheet" href="/assets/site.css">
  <script defer src="/assets/product.js"></script>
</head>
<body>
  <h1>蓝色机械键盘</h1>
  <p class="price">¥299</p>
  <img src="/images/keyboard-blue.webp"
       width="600" height="400" alt="蓝色机械键盘">
  <section id="reviews">用户评论</section>
</body>
</html>
```

响应会带上状态码和内容信息，例如 `200`、`content-type: text/html; charset=utf-8`。如果内容使用 Brotli 压缩，还会有 `content-encoding: br`。浏览器需要先解密，再按内容编码解压，才能解析 HTML。

HTTP/2 请求向下经过各层时，可以这样看：

```text
HTTP/2 HEADERS、DATA 等帧
   ↓ TLS 加密与完整性保护
TLS 字节
   ↓ TCP 组织成报文段
TCP 段
   ↓ IP 封装并寻址
IP 分组
   ↓ 当前链路封装
以太网帧 → 物理信号
```

某个携带应用数据的帧，概念上包含：

```text
[以太网头][IPv4 头][TCP 头][TLS 字节流的一部分][FCS]
```

FCS 是以太网帧的差错检测信息。HTTP/2 帧、TLS 记录、TCP 段的边界不一定对齐，一份 HTTP 响应可能跨越很多个 TCP 段。HTTP/2 的“帧”也是应用层概念，和以太网帧不同。

服务器接收时，按反方向处理：链路层检查帧，IP 层处理分组，TCP 提供连续字节，TLS 验证并解密，HTTP 层解析请求，最后交给网站应用。真实网站也可能先到 CDN 或反向代理，再到后端服务；本文把 HTTPS 入口和应用合并展示。

## 响应途中丢了一段，TCP 怎样处理

IP 不保证分组一定到达，也不保证到达顺序。假设响应发送了四段，第二段丢失：

```text
发送：第 1 段、第 2 段、第 3 段、第 4 段
收到：第 1 段、          第 3 段、第 4 段
```

TCP 可以缓存后续数据，但中间缺口需要补齐。发送方根据确认、丢失检测或超时机制重传，接收方随后继续向上层交付连续字节。

TCP 序号按字节计数。例如某段 `SEQ=1000`，带 500 字节数据，完整连续收到后可确认 `ACK=1500`，意思是接下来期待序号 1500。这个例子独立于前面的握手序号。

发送量也不能无限增加。接收窗口 `rwnd` 表示接收方允许接收的数据范围；拥塞窗口 `cwnd` 是发送方根据网络反馈维护的限制。未确认数据量主要受 `min(rwnd, cwnd)` 约束，能再发多少还要扣除已在途的数据。

TCP 的确认不代表浏览器已经显示内容，只说明相应数据已被接收端 TCP 确认。TCP 也没有应用消息边界，两次 `send()` 不一定对应两次 `recv()`，消息划分由上层协议负责。

## HTML 到达后，浏览器边解析边请求资源

浏览器可以从已经到达的 HTML 开始构建 DOM。DOM 是文档在内存中的结构，例如标题、段落、图片和它们的父子关系。

当解析器发现样式表、脚本和图片，还会发出请求：

```text
GET /assets/site.css
GET /assets/product.js
GET /images/keyboard-blue.webp
```

这些请求可以复用现有 HTTP/2 连接。HTTP/2 用不同的流区分请求和响应，各流的帧可以交错传输：

```text
同一条 TCP / TLS 连接：
CSS 数据 → 图片数据 → JS 数据 → 图片数据 → CSS 数据……
```

这和较早的连接方式不同：

```text
每次新建连接：建连 → 请求 → 响应；再建连 → 请求 → 响应
持久连接串行：一次建连 → 请求 A → 响应 A → 请求 B → 响应 B
HTTP/1.1 流水线：请求 A、B 可先后发出，但响应仍按顺序返回
HTTP/2：多个流的帧可以交错传输
```

HTTP/2 仍依赖一条 TCP 字节流，丢失的字节可能让多个流一起等待。HTTP/3 使用基于 UDP 的 QUIC，把可靠传输等功能放在 QUIC 中，减少这种跨流的传输层队头阻塞。因此，“打开网页一定先建 TCP”只适用于本文选择的访问方式。

## 浏览器怎样把数据画到屏幕上

HTML 描述文档结构，CSS 描述样式，JavaScript 可以改变文档和样式。浏览器还需要计算位置、生成绘制指令，再把结果变成像素：

  .then(data => {

首次显示内容、`DOMContentLoaded`、`load` 和业务数据准备完成，是不同的时刻。页面也不需要先关闭连接才能显示。

## 连接怎样关闭

浏览器可以保留连接，继续请求资源。需要正常关闭时，TCP 的两个发送方向分别结束，常见过程是：

```text
客户端 → 服务器：FIN，我没有更多数据要发送
服务器 → 客户端：ACK，确认

服务器仍可发送剩余数据……

服务器 → 客户端：FIN，我也没有更多数据要发送
客户端 → 服务器：ACK，确认
```

这是常说的四次挥手。ACK 和 FIN 在合适条件下可以合并，因此不必把报文数量理解成固定不变。发送 FIN 后，另一方向仍可以接收数据，这叫半关闭。

常见状态路径如下：

```text
主动建立：CLOSED → SYN-SENT → ESTABLISHED
被动建立：LISTEN → SYN-RECEIVED → ESTABLISHED

主动关闭：ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT → CLOSED
被动关闭：ESTABLISHED → CLOSE-WAIT → LAST-ACK → CLOSED
```

`CLOSE-WAIT` 表示收到对方 FIN，等待本地应用关闭自己的发送方向。`TIME-WAIT` 则保留一段时间，以便回应可能重传的 FIN，并降低旧报文干扰后续连接的风险。经典规则是 2MSL；MSL 是最大报文生存时间，不是一次往返时延。

## 再补几块网络基础

上面的访问过程已经涉及五层。下面这些知识解释了各层为什么需要那些处理。

### 物理层：速率、带宽和传播时延

家庭、办公室通常是局域网 LAN；连接较远地区的网络属于广域网 WAN。电脑可能先通过双绞线或 Wi-Fi 接入，再经过光纤等介质。Wi-Fi 是接入技术，连接上 Wi-Fi 并不自动意味着可以访问互联网。

双绞线、同轴电缆和光纤是常见有线介质；无线通信还包括微波、红外和卫星链路。频分复用 FDM 按频段共享信道，时分复用 TDM 按时间片共享，波分复用 WDM 在光纤中使用不同波长。

载波频率与数据速率是不同概念。真空中波长与频率满足 $\lambda f=c$，介质中则使用对应传播速度。工作在 GHz 频段，不代表数据速率就是同样数值的 Gbit/s。

香农公式给出特定带噪声信道模型下的理论容量：

$$
C=B\log_2(1+S/N)
$$

$B$ 的单位是 Hz，$C$ 的单位是 bit/s，$S/N$ 是信号与噪声功率的线性比值。若 $B=3000$ Hz、$S/N=1000$，容量约为 29.9 kbit/s。30 dB 的信噪比对应线性比值 1000，因为 $\mathrm{SNR}_{dB}=10\log_{10}(S/N)$。

实际吞吐量还要扣除协议等开销。带宽与时延也不同：更高传输速率能缩短发送一大块数据所需的时间，却不能消除信号传播的时间。

### 链路层：帧边界与滑动窗口

接收方需要从连续比特流中识别帧的边界。方法包括记录长度、使用标志字节并转义、使用标志比特并填充，以及使用特殊物理编码符号。

例如某协议用 `01111110` 标记边界，可以在数据中每连续出现五个 `1` 后插入一个 `0`，接收方再删除填充的 `0`，避免数据被误认成边界。

可靠链路协议可以使用滑动窗口，让发送方不必每发一帧就停下来等待确认：

```text
停等：发送 0 → 等待确认 → 发送 1 → 等待确认

窗口大小 4：允许发送 0、1、2、3
确认 0 后： 窗口移动到 1、2、3、4
```

假设第 2 号帧出错：

```text
发送：0、1、2、3、4、5
             ×
Go-Back-N：通常丢弃后续乱序帧，重传缺失处及后续未确认帧
选择重传：缓存 3、4、5，只补发缺失或出错帧
```

选择重传减少重复传输，但需要更多缓存和更复杂的状态管理。链路层不一定都提供这种可靠交付；以太网的 FCS 检错不等于以太网会自动重传。TCP 的窗口和重传发生在端到端传输层。

在速率为 $R$、往返时延为 RTT 的链路上，要充分利用链路，通常需要容纳约 $R\times RTT$ 的在途数据，这叫带宽时延积。

### 网络层：前缀、路由和隧道

IPv4 地址有 32 位。现代路由使用 CIDR 前缀，例如 `/24`，不能只根据传统 A、B、C 类地址判断子网。普通 `/24` 广播子网有 256 个地址，通常 254 个可供主机使用；特殊用途与其他前缀需要单独判断。

```text
主机：192.168.8.34/24
掩码：255.255.255.0
网络：192.168.8.0
广播：192.168.8.255

网络地址 = IP 地址按位 AND 子网掩码
```

连续且对齐的前缀可以聚合。例如 `192.168.8.0/24` 到 `192.168.15.0/24` 共八个前缀，可以用 `192.168.8.0/21` 表示：

```text
第三个字节：
8  = 00001000
15 = 00001111
     00001xxx，共同前缀 5 位

前两个字节 16 位 + 5 位 = /21
```

这是聚合路由，不会自动把八个局域网合并成一个局域网。转发时通常选择匹配目的地址的最长前缀。

路由协议帮助路由器维护路径。距离向量根据邻居报告的距离计算下一跳；链路状态传播邻接关系和代价，再各自计算最短路径。举例说，J 到 C 可以经过 A、I、H、K：

| 经由邻居 | 到邻居的代价 | 邻居报告的到 C 的代价 | 合计 |
|---|---|---|---|
| A | 8 | 25 | 33 |
| I | 10 | 18 | 28 |
| H | 12 | 19 | 31 |
| K | 6 | 36 | 42 |

于是 J 选择 I。对应距离向量的计算式是 $D_x(y)=\min_v\{c(x,v)+D_v(y)\}$。OSPF 是自治系统内部的链路状态协议；BGP 常用于自治系统之间交换路由，选择还受管理与商业策略影响，不保证物理距离或时延最短。自治系统是一组实施统一路由策略的网络。

IP 首部中的 `Protocol` 标识上层协议，例如 TCP 为 6、UDP 为 17；端口则在 TCP/UDP 首部里。IPv4 首部最小 20 字节，首部校验和只检查首部；分片字段处理分片与重组。UDP 首部固定 8 字节，TCP 首部最小 20 字节。

隧道则是在已有分组外再加一层封装。例如让 IPv6 分组穿过 IPv4 网络：

```text
进入前：           IPv6 分组
隧道中：IPv4 头 + IPv6 分组
离开后：           IPv6 分组
```

隧道是否加密，取决于具体协议。SNAT 改源地址，DNAT 改目的地址；例如公网入口 `203.0.113.5:8080` 可以映射到内部服务 `10.0.0.10:80`。本例响应回到电脑时，则依据既有 NAT 状态执行反向转换。

### 传输层：流量控制与拥塞控制

流量控制避免接收方被过量数据塞满，拥塞控制则调整对网络施加的负载。经典 TCP 拥塞控制先慢启动，达到阈值后进入拥塞避免：

```text
慢启动示意：   1 → 2 → 4 → 8
拥塞避免示意： 8 → 9 → 10 → 11
```

慢启动理想情况下约每个 RTT 翻倍；上面的初始值只是教学示例。超时通常触发较大幅度的退让。经典快速重传使用三个重复 ACK 作为丢失线索，快速恢复则在降低发送强度后继续传输。具体实现可能采用其他拥塞控制或丢失检测算法。

端口是服务约定，不是硬性限制。常见的有 SSH 22、DNS 53、HTTP 80、HTTPS 443；FTP 控制连接用 21，主动模式常见服务器数据端口为 20；SMTP 25、POP3 110、IMAP 143、RTSP 554、IPP 631。协议是否安全或流量是否可信，不能只看端口号。

### 应用层：HTTP 方法、状态码和缓存

GET 获取资源表示；HEAD 请求类似 GET 的响应信息但不返回内容；POST 把数据交给资源处理；PUT 创建或替换目标资源状态；DELETE 请求删除相应关联。OPTIONS 查询通信选项，CONNECT 建立隧道，TRACE 用于诊断性回送。POST 不限于“创建”，PUT 也不限于存储网页。

状态码的第一位表示类别：1xx 是中间信息，2xx 成功，3xx 包含重定向和条件请求结果，4xx 表示客户端相关问题，5xx 表示服务器处理失败。`401` 表示缺少有效认证凭据，`403` 表示拒绝执行，`404` 表示未找到资源。

首部把进一步的信息附在请求或响应上：`Content-Type` 表示内容类型，`Content-Encoding` 表示内容编码，`Cookie` 和 `Set-Cookie` 用于携带与设置 Cookie。`Accept` 表达客户端可接收的类型。请求也可以有 `Content-Type` 和 `Content-Length`，不能把它们限定为响应字段。

如果浏览器缓存了一个版本标识为 `"v3"` 的资源，可以用条件请求验证。下面用 HTTP/1.1 文本格式展示同样的语义：

```http
GET /index.html HTTP/1.1
Host: example.com
If-None-Match: "v3"

```

资源未改变时，服务器可以返回：

```http
HTTP/1.1 304 Not Modified
ETag: "v3"
Cache-Control: max-age=60

```

304 仍然发生了一次网络请求，只是避免再次传输完整内容。如果缓存仍然新鲜，浏览器还可能直接使用缓存，连这次验证也省去。
