## 1. 基础概念：分层与数据传递

### 分层模型与封装

浏览器向服务器请求一张图片时，至少涉及这些问题：请求怎么写、数据丢了怎么办、服务器在哪里、下一跳发给谁、如何在网线上传输信号。

网络分层就是把这些问题拆开：

| 五层教学模型 | 核心职责 | 典型例子 |
|---|---|---|
| 应用层 | 定义应用如何交换信息 | HTTP、DNS |
| 传输层 | 在两端的应用之间传输数据 | TCP、UDP |
| 网络层 | 将分组跨网络送向目的地 | IP、路由 |
| 数据链路层 | 在同一条链路上交付帧 | 以太网、Wi-Fi 的链路功能 |
| 物理层 | 通过介质传输比特对应的信号 | 电信号、光信号、无线电波 |

课件还对照了另外两种模型：

- OSI 七层模型：在应用层与传输层之间，还有表示层、会话层。
- TCP/IP 四层模型：应用层、传输层、网际层、链路层。

表示层关注编码、数据表示等，会话层关注会话的建立与管理。TCP/IP 没有把它们作为独立层，并不代表这些功能不存在。

课件后面的章节，基本按照表中的五层教学模型展开。

给数据逐层添加控制信息，叫封装；接收方按相反方向处理，叫解封装。 用未加密的 HTTP over TCP 举例，发送方逐层添加控制信息：

```text
应用层：                    HTTP 数据
传输层：           TCP 头 + HTTP 数据
网络层：    IP 头 + TCP 头 + HTTP 数据
链路层：帧头 + IP 头 + TCP 头 + HTTP 数据 + 帧尾
物理层：将这些比特编码成信号发送
```

接收方反过来逐层处理。

同一层的两端遵循相同协议，可以称为逻辑通信；实际数据仍要经过下面各层才能到达对端。

理解协议关系时，先看谁依赖谁：例如 HTTP 可以依赖 TCP，TCP 再依赖 IP。第一次学习不必记住所有协议缩写。

### LAN、WAN 与接入网

- LAN，局域网：例如家庭、办公室中的网络。
- MAN，城域网：覆盖城市范围的网络。
- WAN，广域网：连接较远地区的网络。
- 接入网：将用户连接到运营商网络的部分。

电脑接入家庭 Wi-Fi，再经过运营商网络访问远处服务器，就是从局部网络走向更大范围的网络。

Wi-Fi 是一种接入技术，互联网是互联起来的网络集合。连接上 Wi-Fi，只能说明你接入了这个无线网络，不一定说明可以访问互联网。

### 面向连接与无连接

| 对比 | 面向连接 | 无连接 |
|---|---|---|
| 通信前 | 先建立连接 | 无须先建立连接 |
| 通信状态 | 双方维护连接状态 | 按独立报文处理 |
| 典型例子 | TCP | UDP、IP |
| 顺序与可靠性 | 取决于具体协议；TCP 提供可靠、有序的字节流 | UDP、IP 本身不保证可靠、有序交付 |

TCP 的“连接”不是在两台机器间预留一根专用网线，而是双方维护序列号、窗口、状态等信息。

另外，TCP 提供的有序性是应用最终读到的数据有序。底层 IP 分组依然可能乱序到达，由 TCP 负责整理。

### 各层反复处理的五类问题

| 问题 | 直观含义 |
|---|---|
| 寻址 Addressing | 数据从谁来、发给谁 |
| 差错控制 Error Control | 发现损坏、丢失，并按协议进行纠正或重传 |
| 流量控制 Flow Control | 避免发送方把接收方的缓冲区塞满 |
| 复用与分用 | 多个通信共享资源，收到后再正确分给各自的应用 |
| 路由 Routing | 决定通往目的地的路径 |

这些问题可能出现在不同层，但处理范围不同。例如链路层处理一段链路上的传输，TCP 处理端到端传输。


## 2. 物理层：把比特变成信号

### 香农公式：带噪声信道的容量上限

公式是：

$$
C=B\log_2\left(1+\frac{S}{N}\right)
$$

其中：

- $C$：理论信道容量，单位是 bit/s。
- $B$：信道带宽，单位是 Hz。
- $S/N$：信号功率与噪声功率之比，必须使用线性比值。

假设：

$$
B=3000\text{ Hz},\qquad S/N=1000
$$

那么：

$$
C=3000\log_2(1001)\approx 29900\text{ bit/s}
$$

也就是大约 $29.9\text{ kbit/s}$。

如果题目给的是分贝，需要先转换：

$$
\mathrm{SNR}_{dB}=10\log_{10}(S/N)
$$

例如 $30\text{ dB}$ 对应 $S/N=1000$。

这个公式揭示了两点：增大频谱带宽可以提高容量；提高信噪比也能提高容量，但收益是对数增长。它给出的是特定信道模型下的理论上限，实际应用吞吐量还会受到编码、协议开销等影响。

这里的“带宽”是 Hz，日常说“100 Mbps 宽带”时的带宽通常指数据传输速率，两者单位不同。

### 有线与无线传输介质

| 介质 | 特点与典型用途 |
|---|---|
| 双绞线 Twisted Pair | 铜线成对绞合，帮助抑制干扰；常见于以太网布线 |
| 同轴电缆 Coaxial Cable | 有中心导体和屏蔽结构；用于有线电视等系统 |
| 光纤 Fiber Optics | 用光传输，容量大、适合长距离、不受电磁干扰 |
| 微波 Microwave | 无线传输；定向链路通常需要考虑视距和遮挡 |
| 红外线 Infrared | 常见于近距离通信，例如遥控器 |
| 通信卫星 | 覆盖范围大；传播时延与轨道高度有关 |

波长与频率的关系是：

$$
\lambda f=c
$$

即在真空中，波长 × 频率 = 光速。在介质中应使用相应传播速度 $v$。

载波频率不等于数据速率。 例如无线信号工作在 GHz 频段，不意味着它就能传输同样数值的 Gbit/s 数据。

### 频分、时分与波分复用

- FDM，频分复用：给不同用户分配不同频段。例如广播电台使用不同频率。
- TDM，时分复用：给不同用户分配不同时间片，轮流使用信道。
- WDM，波分复用：在同一根光纤中同时传输多个不同波长的光信号。

三种方式分别按频率、时间和光的波长分配传输资源。


## 3. 数据链路层：成帧与可靠交付

### 成帧：识别数据的边界

接收方需要借助协议约定，从传入的比特流中识别每一帧的起点和终点。课件介绍了四种方法：

| 方法 | 原理 | 需要注意的问题 |
|---|---|---|
| 字节计数 | 在帧中记录长度 | 长度字段损坏可能导致边界识别错误 |
| 标志字节＋字节填充 | 用特殊字节标记边界，数据中的同类字节需要转义 | 接收方需要撤销转义 |
| 标志比特＋比特填充 | 用特殊比特模式标记边界，修改数据中可能冲突的模式 | 接收方需要删除填充比特 |
| 物理层编码违例 | 使用不会出现在正常数据中的特殊编码符号 | 依赖具体物理编码方案 |

例如，某协议使用 `01111110` 作为帧边界。为了避免数据恰好出现这个模式，发送方在数据中每出现连续五个 `1` 后插入一个 `0`，接收方再删除这个填充的 `0`。

这就是比特填充：让数据内容不会被误认成边界。

### 滑动窗口：允许多帧同时在途

如果每发送一帧都要等待确认：

```text
发送 0 → 等待确认 → 发送 1 → 等待确认 → …
```

在往返时延很大的链路上，发送方会花很多时间等待。

滑动窗口允许同时存在多帧“已经发送但尚未确认”的数据。例如窗口大小为 4：

```text
当前允许发送：0、1、2、3

收到对 0 号帧的确认后：

窗口向前移动：1、2、3、4
```

窗口限制未确认数据量；确认到达后，旧数据移出窗口，新数据获得发送资格。

如果链路速率为 $R$，往返时延为 RTT，那么为了充分利用链路，通常需要能够容纳大约：

$$
R\times RTT
$$

的数据在途中。这就是带宽时延积的直观意义。

### Go-Back-N 与选择重传

这两页内容重复，标题都写了 Go-Back-N，但下方“缓存后续帧、只补发缺失帧”的图展示的是选择重传思想。

假设发送了：

```text
0、1、2、3、4、5
```

其中 2 号帧出错：

| 行为 | Go-Back-N，回退 N | Selective Repeat，选择重传 |
|---|---|---|
| 接收方收到后续的 3、4、5 | 通常丢弃 | 缓存 |
| 重传时 | 从缺失处重传后续未确认帧 | 只重传缺失或出错帧 |
| 接收方缓存需求 | 较低 | 较高 |
| 实现复杂度 | 较简单 | 较复杂 |
| 丢包后的带宽浪费 | 较大 | 较小 |

选择重传允许乱序接收和缓存，但仍可以在缺失帧补齐后，按序向上层交付。


## 4. 网络层：寻址、路由与跨网转发

### 距离向量：根据邻居的距离更新路由

每个路由器维护“到各个目的地的代价”，并与邻居交换信息。

核心公式是：

$$
D_x(y)=\min_v\{c(x,v)+D_v(y)\}
$$

含义是：从 $x$ 到 $y$，尝试经过每一个邻居 $v$，把“到邻居的代价”和“邻居到目的地的代价”加起来，选最小值。

直接使用课件的例子：路由器 J 的邻居是 A、I、H、K。计算 J 到 C：

| 经过邻居 | J 到邻居的代价 | 邻居报告的到 C 的代价 | 总代价 |
|---|---:|---:|---:|
| A | 8 | 25 | 33 |
| I | 10 | 18 | 28 |
| H | 12 | 19 | 31 |
| K | 6 | 36 | 42 |

所以 J 更新路由表：

```text
目的地 C：代价 28，下一跳 I
```

这里的代价可以表示时延、跳数等，取决于协议。

距离向量算法的难点是：路由器依赖邻居的报告，信息更新不及时可能产生环路，以及“无穷计数”等收敛问题。

### 链路状态：根据拓扑计算最短路径

基本过程是：

1. 发现直接相连的邻居。
2. 确定各条链路的代价。
3. 生成链路状态信息。
4. 将信息在相应范围内洪泛传播。
5. 每台路由器根据拓扑图运行最短路径算法，例如 Dijkstra。

链路状态信息中的 `Seq.` 和 `Age` 分别帮助区分新旧信息、淘汰过期信息。

两类算法可以这样对照：

| 距离向量 | 链路状态 |
|---|---|
| 邻居告诉我“它到各处有多远” | 各路由器公布“自己连接谁、代价是多少” |
| 根据邻居的距离更新路由 | 根据拓扑图计算路由 |
| 典型数学基础是 Bellman-Ford | 典型计算方法是 Dijkstra |

### 隧道：在分组外再加一层封装

课件中的场景是：两端使用 IPv6，中间只有 IPv4 网络。

处理方式：

```text
进入隧道前：           IPv6 分组

经过 IPv4 网络时：IPv4 头 + IPv6 分组

离开隧道后：           IPv6 分组
```

中间路由器只需要根据外层 IPv4 头转发，出口再去掉外层封装。

隧道本身表示封装与转发机制，是否加密要看采用的具体协议。

### IPv4 首部：转发所需的信息

IPv4 首部最小为 20 字节，存在选项时可以更长，最大为 60 字节。

| 字段 | 作用 |
|---|---|
| Version | IP 版本，IPv4 中为 4 |
| IHL | 首部长度，以 4 字节为单位；值为 5 表示 20 字节 |
| Total Length | 整个 IPv4 分组的长度，包括首部和数据 |
| Source / Destination Address | 源、目的 IPv4 地址，各 32 位 |
| TTL | 限制分组在网络中继续转发的次数，防止无限循环 |
| Protocol | 指明载荷交给哪种上层协议，例如 TCP 为 6、UDP 为 17 |
| Header Checksum | 检查 IPv4 首部是否损坏 |
| Identification、Flags、Fragment Offset | 支持分片与重组 |
| Differentiated Services | 与服务区分、拥塞通知等有关 |

两个容易混淆的地方：

- Protocol 字段不是端口号：它先决定交给 TCP 还是 UDP；端口再决定交给哪个应用端点。
- IPv4 首部校验和不覆盖数据载荷。

分片相关字段中，DF 表示不允许分片，MF 表示后面还有分片，分片偏移以 8 字节为单位。

### IP 地址：从分类地址到 CIDR

课件给出传统分类：

- A 类：默认网络前缀 `/8`。
- B 类：默认网络前缀 `/16`。
- C 类：默认网络前缀 `/24`。
- D 类：组播地址。
- E 类：保留用途。

现代 IPv4 分配与路由采用无类别前缀，不能仅凭地址开头推断子网掩码；应读取明确的 `/n`。课件分类图中的范围也包含特殊用途地址，例如 `127.0.0.0/8` 用于回环，不能当作普通公网主机地址。[CIDR 标准说明](https://www.rfc-editor.org/rfc/rfc4632.html)

例如：

```text
192.168.8.34/24
```

表示前 24 位是网络前缀，剩余 8 位是主机部分。

### 子网与路由聚合

先看一个 `/24`：

```text
主机地址：192.168.8.34/24
子网掩码：255.255.255.0
网络地址：192.168.8.0
广播地址：192.168.8.255
```

普通 IPv4 广播子网中，这个 `/24` 有 256 个地址，通常有 254 个可分配给主机。

网络地址可以通过按位与计算：

$$
\text{网络地址}=\text{IP 地址}\ \&\ \text{子网掩码}
$$

课件图实际重点展示的是路由聚合：把下面 8 个连续、对齐的 `/24` 前缀：

```text
192.168.8.0/24
192.168.9.0/24
…
192.168.15.0/24
```

聚合为：

```text
192.168.8.0/21
```

因为 8 个网络需要 3 位区分，所以前缀从 24 位缩短为：

$$
24-\log_2 8=21
$$

第三个字节从 8 到 15：

```text
8  = 00001000
15 = 00001111
     └───┘
     前 5 位相同
```

加上前两个字节的 16 位，共同前缀就是 21 位。

这个聚合前缀覆盖 `192.168.8.0` 到 `192.168.15.255`。聚合路由不会自动把原来的多个局域网合并成一个局域网。

### SNAT 与 DNAT

课件画的是内网设备访问外网：

```text
转换前的源：10.0.0.1:5544
转换后的源：198.60.42.12:3344
```

这是源地址转换；图中连端口也改变了，因此同时展示了端口转换。

- SNAT：改变源地址，常见于内网主机访问外网。
- DNAT：改变目的地址，常见于将公网入口映射到内部服务器。

例如 DNAT：

```text
外部请求：203.0.113.5:8080
内部目标：10.0.0.10:80
```

转换设备维护映射状态，收到返回流量后执行相应的反向转换。多个内网连接因此可以共享一个公网地址。

### ARP、RARP 与 DHCP

ARP 用于在本地链路上，根据 IPv4 地址寻找对应的链路层地址，常见情况就是 MAC 地址。

例如，电脑需要向同一局域网的 `192.168.1.20` 发帧，就可以广播询问：“谁使用这个 IP？”

如果目标在外网，电脑通常需要查询的是下一跳默认网关的 MAC 地址。帧先交给网关，IP 分组的目的地址仍然是远端服务器。

RARP 是历史协议，帮助设备根据自己的硬件地址获取 IP 地址，曾用于无盘工作站启动等场景。

DHCP 自动提供网络配置，包括 IP 地址、子网掩码、默认网关、DNS 服务器等。经典首次获取过程称为 DORA：

```text
Discover → Offer → Request → ACK
发现服务器 → 提供配置 → 请求选定配置 → 确认分配
```

地址通常带租约，到期前需要续租。课件写“登录服务器后获得地址”不够准确，DHCP 配置过程不要求用户先登录服务器。[DHCP 协议流程](https://www.rfc-editor.org/rfc/rfc2131.html)

### OSPF 与 BGP

自治系统 AS 可以理解为由同一管理实体实施统一路由策略的一组网络，例如某运营商管理的网络。

| 协议 | 主要角色 | 核心思想 |
|---|---|---|
| OSPF | 自治系统内部路由 | 链路状态、最短路径计算、区域划分 |
| BGP | 自治系统之间交换路由 | 路径属性与路由策略 |

OSPF 可以将较大的路由网络划分为多个区域，并通过骨干区域组织区域间通信。

BGP 会携带 AS 路径等属性。它的选择结果受到商业关系和管理策略影响，不能简单理解成永远选择物理距离最短或时延最低的路线。


## 5. 传输层：端点、可靠性与发送控制

### 端口与通信端点

一台主机可能同时运行浏览器、SSH 客户端和邮件程序。IP 地址只提供网络层地址，传输层还需要端口来区分通信端点。

一条 TCP 连接通常由四元组区分：

```text
源 IP、源端口、目的 IP、目的端口
```

例如：

```text
192.168.1.10:51000 → 203.0.113.20:443
192.168.1.10:51001 → 203.0.113.20:443
```

它们可以是不同连接，因此一个服务器的 443 端口能够同时服务很多连接。

### UDP：保留报文边界的传输

UDP 首部固定 8 字节，包含四个各 16 位的字段：

| 字段 | 作用 |
|---|---|
| Source Port | 源端口 |
| Destination Port | 目的端口 |
| Length | UDP 首部与数据的总长度 |
| Checksum | 用于差错检测 |

UDP 保留报文边界，但本身不负责重传、不保证按序交付，也不提供 TCP 那样的连接管理和流量控制。

因此，UDP 应用需要根据需求自己处理丢失、顺序、发送速率等问题。DNS 查询、实时音视频，以及建立在 UDP 之上的其他传输协议，都可能使用 UDP。

“UDP 开销小”不等于“所有应用使用 UDP 都一定更快”。

### 常见服务端口

| 端口 | 服务 |
|---|---|
| 21 | FTP 控制连接 |
| 20 | FTP 主动模式中的常见服务器数据端口 |
| 22 | SSH |
| 25 | SMTP |
| 80 | HTTP |
| 110 | POP3 |
| 143 | IMAP |
| 443 | HTTPS |
| 554 | RTSP |
| 631 | IPP 打印协议 |

课件将 RTSP 写成了 543，这是笔误，应为 554。[IANA 端口登记](https://www.iana.org/assignments/service-names-port-numbers?search=554)

这些是常见默认值，服务可以配置到其他端口。

### TCP 首部与字节序号

TCP 首部最小为 20 字节。重点字段有：

- Sequence Number：本段数据的起始字节序号。
- Acknowledgment Number：接收方接下来期望收到的序号。
- Window：接收方通告的接收窗口。
- Checksum：对 TCP 首部、数据以及伪首部信息进行差错检测。
- Flags：例如 SYN、ACK、FIN、RST。
- Options：例如最大报文段长度、窗口扩大、时间戳等。

TCP 的序号按字节计数。假设发送：

```text
SEQ = 1000
数据长度 = 500 字节
```

那么这些数据的序号是 1000–1499。接收方完整、连续收到后，通常确认：

```text
ACK = 1500
```

含义是：“1500 之前的数据已连续收到，接下来期待 1500。”

TCP 提供的是字节流，没有应用消息边界。发送方调用两次 `send()`，接收方不一定对应两次 `recv()`；应用需要通过长度字段、分隔符等方式识别自己的消息边界。

### TCP 三次握手

![TCP 三次握手：客户端初始序号 100，服务器初始序号 500，双方确认彼此的序号。](/blog/from-url-to-webpage/handshake-basics-zh.svg)

三次握手示意。[查看大图](/blog/from-url-to-webpage/handshake-basics-zh.svg) · [Mermaid 源文件](/blog/from-url-to-webpage/handshake-basics-zh.mmd)

过程是：

1. 客户端提出建立连接，并公布自己的初始序号。
2. 服务器确认客户端的序号，同时公布自己的初始序号。
3. 客户端确认服务器的序号。

第三步使服务器知道：客户端已经收到并确认了自己的连接建立信息。它也帮助避免旧的连接请求直接造成错误的连接建立。

SYN 会占用一个序号，所以图中的确认号需要加 1。

### TCP 关闭与半关闭

```text
客户端 → 服务器：FIN，我没有更多数据要发送
服务器 → 客户端：ACK，确认你的发送方向结束

服务器仍可发送剩余数据……

服务器 → 客户端：FIN，我也没有更多数据要发送
客户端 → 服务器：ACK，确认你的发送方向结束
```

客户端发出 FIN 后，其接收方向仍可能继续接收服务器的数据，这称为半关闭。

“四次”是典型过程；如果服务器能够把 ACK 和自己的 FIN 合并发送，实际报文数量可以减少。FIN 和 SYN 一样，也会占用一个序号。

### TCP 状态机

先掌握最常见的路径即可：

```text
主动建立：
CLOSED → SYN-SENT → ESTABLISHED

被动建立：
LISTEN → SYN-RECEIVED → ESTABLISHED

典型主动关闭：
ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT → CLOSED

典型被动关闭：
ESTABLISHED → CLOSE-WAIT → LAST-ACK → CLOSED
```

其中两个状态尤其值得区分：

- CLOSE-WAIT：已经收到对方的 FIN，等待本地应用关闭自己的发送方向。大量长期停留的连接可能提示应用没有及时关闭连接。
- TIME-WAIT：正常主动关闭路径中，发送最后确认的一方还要保留一段时间，以便回应可能重传的 FIN，并降低旧报文干扰后续连接的风险。

经典规则是等待 2MSL，这里 MSL 是最大报文生存时间，不能把它理解为两倍 RTT。[TCP 关闭与 TIME-WAIT 规则](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6)

### 流量控制与拥塞控制

先区分两个窗口：

| 窗口 | 解决的问题 | 谁决定 |
|---|---|---|
| 接收窗口 `rwnd` | 接收方还能接收多少数据 | 接收方通告 |
| 拥塞窗口 `cwnd` | 网络目前适合承载多少未确认数据 | 发送方根据反馈调整 |

未确认数据量主要受以下上限约束：

$$
\min(rwnd,cwnd)
$$

还能够发送多少新数据，需要再扣除已经发送但未确认的数据量。TCP 首部中的 Window 字段对应接收窗口，拥塞窗口是发送方维护的内部状态。

课件展示的是经典拥塞控制过程：

| 阶段 | 窗口变化的直观规律 |
|---|---|
| 慢启动 | 从较小窗口开始，在理想条件下约每个 RTT 翻倍 |
| 拥塞避免 | 达到阈值后，改为大致线性增长 |
| 超时重传 | 大幅降低窗口，重新慢启动 |
| 快速重传、快速恢复 | 利用重复 ACK 尽早发现疑似丢包，并降低发送强度 |

教学例子可以写成：

```text
慢启动：   1 → 2 → 4 → 8
拥塞避免： 8 → 9 → 10 → 11
```

这里从 1 开始是简化示例，不代表所有实现的初始窗口都是 1。

经典快速重传使用 3 个重复 ACK 作为丢失线索，在超时之前重传。快速恢复则避免每次都从极小窗口重新开始。具体的 Reno 算法还包含恢复期间的临时窗口调整。[经典 TCP 拥塞控制](https://www.rfc-editor.org/rfc/rfc5681.html)


## 6. 应用层：DNS 与 HTTP

### DNS 名字空间

以课件里的域名为例：

```text
robot.cs.washington.edu.
```

从右向左看：

```text
.               根
edu             顶级域
washington      下一级域
cs              再下一级域
robot           具体名称
```

末尾的点表示 DNS 根，日常输入通常省略。

这种结构允许不同组织分别管理自己的部分，不需要由一台服务器维护互联网上所有名字。

还要区分域名与 URL：

```text
https://www.example.com/course?id=19
        └── 域名 ────┘└─ 路径与查询 ─┘
```

DNS 主要处理名字解析，不负责解释 `/course?id=19` 的应用含义。

### DNS 资源记录

| 类型 | 作用 |
|---|---|
| A | 名称对应的 IPv4 地址 |
| AAAA | 名称对应的 IPv6 地址 |
| CNAME | 名称的别名，指向另一个名称 |
| MX | 接收邮件的服务器及优先级 |
| NS | 某个区域的权威名称服务器 |
| SOA | 区域的管理信息，例如序列号、刷新参数 |
| PTR | 反向解析中使用的名称指针 |
| TXT | 文本信息，常用于验证、邮件策略等 |
| SRV | 服务位置，包括目标、端口、优先级等 |

CNAME 指向的是名称，不能直接把它理解成另一种 IP 地址记录。

课件还列出了独立的 SPF 记录类型。这属于历史内容；SPF 策略应发布在 TXT 记录中，独立 SPF RR 类型的使用已被停止。[SPF 标准说明](https://www.rfc-editor.org/rfc/rfc7208.html#section-3.1)

### DNS 查询与缓存

假设缓存没有结果，要解析 `robot.cs.washington.edu`：

1. 计算机向配置的递归解析器提出查询。
2. 解析器询问根服务器，获得 `.edu` 的服务器线索。
3. 询问 `.edu` 服务器，获得 `washington.edu` 的服务器线索。
4. 继续沿委派关系查询，例如找到负责 `cs.washington.edu` 的服务器。
5. 获得结果后返回给客户端，并按规则缓存。

这里：

- 客户端要求递归解析器帮自己得到结果。
- 解析器向其他服务器逐步查询的过程通常是迭代查询。

根服务器通常返回下一步该问谁，并不直接保存所有主机的 IP 地址。

缓存使后续查询不必每次都从根开始。DNS 记录的 TTL 表示缓存有效时间，它与 IP 首部中限制转发次数的 TTL 含义不同。

### 点击链接时，各层怎样协作

课件用一次普通 HTTP 访问说明协议协作。补上 HTTPS 的 TLS 后，可以概括为下面几步；文末的商品页案例会展开这些步骤：

1. 解析 URL：识别协议、域名、端口、路径。
2. 检查缓存并进行 DNS 解析：得到目标 IP 地址。
3. 选择路由和下一跳：判断是否通过默认网关。
4. 准备链路层交付：在需要时通过 ARP 获取下一跳的 MAC 地址。
5. 建立 TCP 连接：进行三次握手。
6. 建立 TLS 安全会话：完成相应身份验证和密钥协商。
7. 发送 HTTP 请求：例如请求 `/index.html`。
8. 接收 HTTP 响应：获取 HTML 等内容。
9. 继续请求依赖资源并渲染：处理 CSS、JavaScript、图片等。

这些步骤不是每次点击都要从头执行：DNS 可能命中缓存，连接可能被复用，资源也可能已经缓存。实际顺序也有依赖关系，例如向外网发送 DNS 查询之前，可能已经需要通过 ARP 查找网关的 MAC。

课件中“打开网页先建立 TCP”的流程适用于它讨论的 HTTP over TCP。HTTP/3 使用 QUIC；QUIC 建立在 UDP 之上，并提供可靠流传输等能力。[HTTP/3 标准](https://www.rfc-editor.org/rfc/rfc9114.html)

### HTTP 连接复用

课件比较了三种连接使用方式：

| 方式 | 工作过程 | 主要问题或收益 |
|---|---|---|
| 每次使用新连接 | 建连 → 请求 → 响应，之后重新建连 | 重复承担建连成本 |
| 持久连接、顺序请求 | 保留连接，一个响应完成后再发下一个请求 | 节省建连成本，但请求仍串行 |
| 持久连接、流水线请求 | 不等前一个响应就发送后续请求 | 减少请求等待，但响应顺序仍受约束 |

HTTP/1.1 流水线并不等同于 HTTP/2 多路复用。

HTTP/2 引入流与帧，允许多个请求响应在一条连接上交错传输；不过使用 TCP 时，丢失的数据仍可能让多个流一起等待。HTTP/3 将流机制建立在 QUIC 上，减少了这种跨流的传输层队头阻塞。[HTTP 版本的传输差异](https://www.rfc-editor.org/rfc/rfc9114.html#section-1)

### HTTP 方法与状态码

课件对方法的描述比较简略，可以更准确地理解为：

| 方法 | 含义 |
|---|---|
| GET | 获取资源的表示 |
| HEAD | 获取类似 GET 的响应元信息，但不返回响应内容 |
| POST | 将数据交给目标资源，按其语义处理 |
| PUT | 用请求中的表示创建或替换目标资源状态 |
| DELETE | 请求删除目标资源与当前功能的关联 |
| OPTIONS | 查询通信选项 |
| CONNECT | 建立隧道，常用于代理场景 |
| TRACE | 请求诊断性的回送信息 |

因此，POST 不只是“向网页追加内容”，PUT 也不只是“存储网页”；HTTP 可以操作 JSON API 等多种资源。[HTTP 方法语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3)

补充一个常用概念：幂等性指同一个请求执行多次，其预期效果与执行一次相同。例如重复 PUT 同一份资源内容；它不要求每次返回的状态码完全一样。

状态码分为五组：

| 范围 | 含义 | 示例 |
|---|---|---|
| 1xx | 中间信息 | 100 Continue |
| 2xx | 成功 | 200 OK、201 Created、204 No Content |
| 3xx | 重定向或条件请求相关结果 | 301、302、304 |
| 4xx | 请求存在客户端相关问题 | 400、401、403、404 |
| 5xx | 服务器处理失败 | 500、502、503、504 |

几个常见区别：

- `401`：缺少有效的认证凭据。
- `403`：服务器理解请求，但拒绝执行。
- `404`：没有找到请求的资源。
- `304`：条件请求下资源未修改，可以继续使用已有缓存；它不是普通的跳转响应。
- `204`：请求成功，但没有响应内容。

### HTTP 首部与缓存验证

按用途理解，比逐个死记更容易：

| 用途 | 典型字段 |
|---|---|
| 请求目标与客户端信息 | `Host`、`User-Agent`、`Referer` |
| 内容协商 | `Accept`、`Accept-Encoding`、`Accept-Language` |
| 身份与状态 | `Authorization`、`Cookie`、`Set-Cookie` |
| 内容描述 | `Content-Type`、`Content-Length`、`Content-Encoding` |
| 缓存与条件请求 | `Cache-Control`、`ETag`、`If-None-Match`、`Last-Modified`、`If-Modified-Since` |
| 跳转和范围请求 | `Location`、`Range`、`Content-Range`、`Accept-Ranges` |

几个字段需要成对理解：

- `Accept`：“我可以接收哪些类型”；`Content-Type`：“这份内容是什么类型”。
- `Accept-Encoding`：“我支持哪些内容编码”；`Content-Encoding`：“这份内容实际使用什么编码”，例如 gzip。
- `Set-Cookie`：服务器要求客户端保存 Cookie；`Cookie`：客户端按规则在后续请求中携带。
- `ETag`：服务器给出的表示版本标识；`If-None-Match`：客户端拿已有标识进行条件查询。

课件表格里的 Request/Response 分类不能一概而论。例如，POST 请求也可以有 `Content-Type` 和 `Content-Length`。

以 HTTP/1.1 为例，一个请求可以写成：

```http
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html
Accept-Encoding: gzip
If-None-Match: "v3"

```

首部后面有一个空行，用于结束首部部分。

如果服务器确认目标表示仍然符合 `"v3"`，可以返回：

```http
HTTP/1.1 304 Not Modified
ETag: "v3"
Cache-Control: max-age=60

```

这时浏览器继续使用已有的缓存内容。304 仍然发生了一次网络请求，只是避免了再次传输完整资源；如果缓存仍然新鲜，浏览器还可能直接使用缓存，连这次验证请求也不发送。

## 补充案例：用一次商品页访问串起各层

下面的案例用于回看前面的分层、寻址与协议职责。假设电脑通过网线连接家用路由器，使用 IPv4，没有可用的 DNS、网页缓存或已有连接。DNS 使用普通 UDP，网站使用 HTTP/2、TLS 1.3 与 TCP。域名、公网地址和端口映射都是教学示例。

输入网址后，目标页面显示蓝色机械键盘的名称、价格、图片和评论区：

```text
https://shop.example.com/products/42?color=blue#reviews
```

| 角色 | 地址 |
|---|---|
| 电脑 | `192.168.1.10/24` |
| 默认网关，路由器 LAN 接口 | `192.168.1.1` |
| 路由器 WAN 接口 | `198.51.100.23` |
| DNS 递归解析器 | `192.0.2.53` |
| 网站服务器，稍后由 DNS 查到 | `203.0.113.80` |

### 入网配置与 URL 解析

DHCP 预先解决四个配置问题：

```text
我自己的 IP 是多少？
哪些地址和我在同一个子网？
访问外网应该交给谁？
应该找谁查询 DNS？
```

本例由家用路由器提供 DHCP 服务，客户端使用 UDP 68，服务器使用 UDP 67：

```text
电脑                         DHCP 服务器
 │── DHCP Discover ────────────→│
 │←─ DHCP Offer ────────────────│
 │── DHCP Request ─────────────→│
 │←─ DHCP ACK ──────────────────│
```

获得的配置如下。DHCP 发生在获取或更新租约时，不会随每次网页访问重新执行。

```text
IP 地址：     192.168.1.10
子网掩码：    255.255.255.0
默认网关：    192.168.1.1
DNS 服务器：  192.0.2.53
```

浏览器再解析 URL：

| 部分 | 值 | 用途 |
|---|---|---|
| Scheme | `https` | 使用 HTTPS |
| Host | `shop.example.com` | 主机名 |
| Port | 默认 `443` | 服务端口 |
| Path | `/products/42` | 资源路径 |
| Query | `color=blue` | 查询参数 |
| Fragment | `reviews` | 页面内定位 |

```text
我要通过 HTTPS，
访问 shop.example.com 的 443 端口，
请求 /products/42?color=blue。
```

片段 `#reviews` 不会作为 URL 的一部分发送给服务器，浏览器在页面内容可用后自行处理。

### DNS 请求发出前，先解决路由与 ARP

需要查询的问题是：

```text
shop.example.com 的 IPv4 地址是什么？
```

这次查询使用的端点是：

```text
源：192.168.1.10:53000
目的：192.0.2.53:53
传输协议：UDP
```

本地子网与选中的路由分别是：

```text
192.168.1.0/24
```

```text
默认路由 → 下一跳 192.168.1.1
```

由于 DNS 服务器在外网，分组先交给网关。若没有网关的 ARP 缓存，电脑在本地广播：

```text
谁的 IP 是 192.168.1.1？
请告诉 192.168.1.10 你的 MAC 地址。
```

路由器回复，电脑记录映射：

```text
192.168.1.1 是我，
我的 MAC 地址是 02:00:00:00:00:01。
```

```text
192.168.1.1 → 02:00:00:00:00:01
```

两层的目的地址因此不同：

```text
IP 目的地址： DNS 服务器的 IP
帧目的 MAC：  网关的 MAC
```

ARP 不经过 TCP/UDP，也没有端口。电脑只需知道这一跳的 MAC，不需要知道远端 DNS 服务器的 MAC。因此，本例的 ARP 发生在 DNS 查询发出去之前。

### DNS 查询的封装与解析

请求逐层加上首部，最终编码为信号：

```text
应用层
DNS 查询：shop.example.com 的 A 记录是什么？

       ↓ 加 UDP 首部

传输层
UDP：源端口 53000，目的端口 53

       ↓ 加 IPv4 首部

网络层
IPv4：源 192.168.1.10，目的 192.0.2.53

       ↓ 加以太网首部、帧尾

数据链路层
以太网：源 MAC 是电脑，目的 MAC 是网关

       ↓ 编码、调制为信号

物理层
通过网线发送电信号
```

路由器取出 IP 分组并继续转发，同时为这条 UDP 通信建立 NAT 映射。若解析器也没有缓存，它沿域名层级查询：

```text
电脑
  │
  │ shop.example.com 的地址是什么？
  ↓
递归解析器
  │
  ├─ 问根服务器
  │    → 获得 .com 名称服务器的线索
  │
  ├─ 问 .com 名称服务器
  │    → 获得 example.com 权威服务器的线索
  │
  └─ 问 example.com 权威服务器
       → shop.example.com 的 A 记录是 203.0.113.80
```

解析结果与网站服务端点是：

```text
shop.example.com → 203.0.113.80
```

```text
目标服务：203.0.113.80:443
```

解析器向根、顶级域和权威服务器发出的，是使用自己网络端点的新查询。结果可以按 DNS TTL 缓存。

### TCP 连接经过 NAT 与逐跳转发

电脑选择临时 TCP 端口 51514：

```text
192.168.1.10:51514 → 203.0.113.80:443
```

路由器将它映射到公网端点，服务器看到转换后的源：

```text
TCP 连接的内部端点             对外使用的端点
192.168.1.10:51514    ↔    198.51.100.23:62001
```

```text
198.51.100.23:62001
```

分组沿途经过：

```text
电脑 → 家用路由器 → 运营商网络 → 其他网络 → 网站所在网络 → 服务器
```

普通路由器查转发表选择下一跳，递减 IPv4 TTL，并按出链路重新封装。OSPF、BGP 帮助维护路由信息；普通二层交换机转发帧时通常不会改写源、目的 MAC。

![商品页 TCP 三次握手，客户端初始序号为 1000，服务器初始序号为 8000。](/blog/from-url-to-webpage/handshake-example-zh.svg)

具体访问中的三次握手，每条箭头都经过底层网络。[查看大图](/blog/from-url-to-webpage/handshake-example-zh.svg) · [Mermaid 源文件](/blog/from-url-to-webpage/handshake-example-zh.mmd)

此时得到的是可靠、有序的字节流连接。服务器身份验证与通信加密由下一步的 TLS 完成。

### TLS 握手：验证身份与派生密钥

下面是 TLS 1.3 完整证书握手的主要交互：

```text
浏览器                                      服务器
  │── ClientHello ───────────────────────────→│
  │   支持的版本、算法、临时密钥交换信息等       │
  │                                           │
  │←─ ServerHello ────────────────────────────│
  │←─ 加密扩展、证书、签名证明、Finished ───────│
  │                                           │
  │ 验证证书与握手消息                         │
  │── Finished ──────────────────────────────→│
  │                                           │
  │←──────── 加密的应用数据 ──────────────────→│
```

浏览器检查证书域名、信任链、有效期，以及服务器的签名证明。双方利用临时密钥交换结果派生通信密钥，后续数据使用对称加密与完整性保护。证书公钥不是用来直接加密整份网页的。

SNI 表明目标服务器名称；ALPN 协商应用协议，本例选择 `h2`，即 HTTP/2。这些是对课件 HTTP 例子的 HTTPS 补充。[TLS 1.3 握手](https://www.rfc-editor.org/rfc/rfc8446.html#section-2)

### HTTP 请求、服务器处理与响应

完成 HTTP/2 初始化后，请求字段的可读形式如下。实际在线上传输的是二进制帧：

```text
:method: GET
:scheme: https
:authority: shop.example.com
:path: /products/42?color=blue
accept: text/html
accept-encoding: gzip, br
```

请求的应用含义是：

```text
请给我 42 号商品的蓝色版本页面。
我希望收到 HTML，也支持相应的内容压缩。
```

向下封装的过程和一个以太网帧的概念结构如下：

```text
HTTP/2：把请求编码成 HEADERS 等帧
   ↓
TLS：加密、添加完整性保护
   ↓
TCP：把字节流组织成报文段
   ↓
IP：添加源、目的 IP 等网络层信息
   ↓
以太网：封装成发往网关的帧
   ↓
物理层：通过信号发送
```

```text
[以太网头][IPv4 头][TCP 头][TLS 字节流的一部分][FCS]
```

HTTP/2 帧、TLS 记录、TCP 段与以太网帧的边界不必对齐。[HTTP/2 帧与流](https://www.rfc-editor.org/rfc/rfc9113.html#section-2) 服务器按相反方向处理，再交给网站应用：

```text
物理层恢复信号中的比特
   ↓
网卡与链路层识别帧、检查 FCS
   ↓
IP 层处理发给本机的分组
   ↓
TCP 根据连接信息接收、排序、去重，交付连续字节
   ↓
TLS 验证并解密
   ↓
HTTP/2 解析请求
   ↓
网站应用处理 /products/42?color=blue
```

```text
查找商品 42
→ 选择蓝色款式
→ 读取名称、价格和图片地址
→ 生成 HTML
```

假设应用生成下面的 HTML：

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <link rel="stylesheet" href="/assets/site.css">
  <script defer src="/assets/product.js"></script>
</head>
<body>
  <h1>蓝色机械键盘</h1>
  <p class="price">¥299</p>
  <img src="/images/keyboard-blue.webp"
       width="600" height="400" alt="蓝色机械键盘">
  <section id="reviews">用户评论</section>
</body>
</html>
```

响应字段可能是：

```text
:status: 200
content-type: text/html; charset=utf-8
content-encoding: br
```

内容按声明压缩，再经 TLS、TCP/IP 返回。为便于跟踪，例子把 HTTPS 入口和应用合并成一个服务器；实际网站也可能经过 CDN 或反向代理。

### 响应回程、丢包与资源复用

响应在公网中，以及经过反向 NAT 后的端点分别是：

```text
203.0.113.80:443 → 198.51.100.23:62001
```

```text
203.0.113.80:443 → 192.168.1.10:51514
```

如果第二段丢失：

```text
发送顺序：第 1 段、第 2 段、第 3 段、第 4 段
实际收到：第 1 段、          第 3 段、第 4 段
```

TCP 可以缓存后续数据，等待重传补齐缺口后继续交付连续字节。发送量受两类限制：

```text
接收方有没有空间？ → 流量控制、接收窗口
网络能否承受？     → 拥塞控制、拥塞窗口
```

TCP 确认收到数据，不等于浏览器已经显示内容。浏览器还要完成解密、解压与解析，并发现这些依赖：

```html
<link rel="stylesheet" href="/assets/site.css">
<script defer src="/assets/product.js"></script>
<img src="/images/keyboard-blue.webp">
```

于是产生资源请求，它们可以复用同一条 HTTP/2 连接：

```text
GET /assets/site.css
GET /assets/product.js
GET /images/keyboard-blue.webp
```

```text
同一条 TCP/TLS 连接中：

CSS 数据 → 图片数据 → JS 数据 → 图片数据 → CSS 数据……
```

不同流的帧可以交错传输，但 TCP 字节流的缺口仍可能让多个流等待。

### 浏览器渲染与后续请求

HTML 生成 DOM，CSS 参与样式计算，随后才能确定布局并绘制：

![HTML、CSS 与 JavaScript 参与浏览器处理，经过布局、绘制、栅格化与合成后显示页面。](/blog/from-url-to-webpage/rendering-zh.svg)

浏览器渲染的主要依赖关系。[查看大图](/blog/from-url-to-webpage/rendering-zh.svg) · [Mermaid 源文件](/blog/from-url-to-webpage/rendering-zh.mmd)

DOM 是文档结构；布局计算位置和尺寸；绘制生成指令；栅格化与合成生成并组合像素。下载与渲染可以交错，页面不必等全部资源到齐才显示。[浏览器解析与渲染过程](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/How_browsers_work#render)

本例的 `defer` 脚本下载时不阻塞 HTML 解析；图片宽高让浏览器提前留出空间；评论区元素可用后，再处理 `#reviews` 定位。

页面显示后，脚本还可能查询库存：

```javascript
fetch("/api/stock?product=42")
  .then(response => response.json())
  .then(data => {
    // 根据库存结果更新页面
  });
```

这个请求再次经过各层，并可能触发页面更新：

```text
HTTP 请求
→ TLS
→ TCP
→ IP
→ 链路层
→ 物理层
→ 服务器
→ 响应返回
→ JavaScript 更新 DOM
→ 必要的样式、布局、绘制更新
```

首次显示内容、`DOMContentLoaded`、`load` 与业务数据就绪是不同的时刻。页面显示也不要求 TCP 立即关闭，连接可以继续复用。

### 完整时序图：一起跟踪 IP、MAC 与端口

这张图把上面的步骤放在同一条时间线上。MAC 用接口代号表示；互联网中的多个路由跳点折叠展示。TLS 与 HTTP 使用端到端箭头，但仍经过相同的网关与路由路径。

| MAC 代号 | 对应接口 |
|---|---|
| `C` | 电脑网卡 |
| `GL` / `GW` | 家用路由器的 LAN / WAN 接口 |
| `I` | 运营商第一跳路由器接口 |
| `RD` / `RS` | DNS / 网站链路的最后一跳路由器接口 |
| `D` / `S` | DNS / 网站服务器网卡 |

![完整时序图展示 ARP、DNS、TCP、TLS、HTTP 交互与浏览器渲染，标明逐跳 IP、MAC 和端口变化。](/blog/from-url-to-webpage/full-sequence-zh.svg)

完整时序图，建议打开大图查看地址细节。[查看大图](/blog/from-url-to-webpage/full-sequence-zh.svg) · [Mermaid 源文件](/blog/from-url-to-webpage/full-sequence-zh.mmd)

| 字段 | 电脑发出 | NAT 后进入公网 | 普通路由转发 | 返回家庭网络 |
|---|---|---|---|---|
| IP | 源为电脑内网 IP | 源改为路由器公网 IP | 地址通常保持，TTL 递减 | 目的改回电脑内网 IP |
| TCP 端口 | 源端口 51514 | 源端口改为 62001 | 保持不变 | 目的端口改回 51514 |
| MAC | C → GL | GW → I | 每个路由跳点重新封装 | 最后一跳 GL → C |

图中 UDP 查询使用 `53000 ↔ 63000` 的 NAT 映射；它与 TCP 的 `51514 ↔ 62001` 是两条不同映射。NAT 负责地址与端口转换，TLS 负责加密，TCP 负责可靠字节流，它们分别解决不同层面的问题。
