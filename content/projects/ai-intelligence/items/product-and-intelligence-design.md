MATRIX 的核心需求是：**几分钟掌握重要变化，持续追踪项目，再通过证据理解趋势并形成判断。** 内容数量不是成功指标。用户能否说清“变了什么、为什么重要、依据在哪里、下一步做什么”，才决定产品有没有用。

本文记录 2026-09-27 的本地 v2 实现与确认过的产品决策，不代表线上站点已经部署这一版本。源码与知识库归属 [AI Intelligence 仓库](https://github.com/Derekwang2002/ai-intelligence)；Derek Hub 保存设计说明，不复制持续变化的情报数据。

## 1. 用阅读路径组织功能

| 入口 | 用户要完成的事 | 设计约束 |
| --- | --- | --- |
| 今日 | 快速知道重要变化 | 必读最多五条，说明入选理由，不强行填满 |
| 事件 | 找到具体事实与发布 | 搜索、分类、已核实动态、前沿观察；保留永久地址 |
| 项目 | 持续追踪同一个产品或技术 | 当前判断、近期变化、可用性、场景、时间线、来源、待验证问题 |
| 洞察 | 理解证据累积后的判断 | 趋势、技术雷达、研究专题三个二级入口 |
| 关注 | 回到自己的工作上下文 | 关注项目、趋势、专题与场景，同时保留全局重大变化 |

日报归档从今日进入，来源覆盖从资料截至时间和页脚进入。搜索覆盖事件、项目、趋势和专题。首页把更新流作为主体，桌面右侧放覆盖状态、持续研究和场景入口；手机按阅读顺序堆叠。

**一次核心阅读必须有终点。** 用户读完可明确标记已读，更多内容通过分页或展开进入，不用无限滚动把简报变成信息流。

## 2. 未读跟踪变化，不只跟踪文章

同一事件可以在多个运行中更新，但始终是一个实体。所选范围内的更新合并展示，历史留在展开区域。新增、重大更新、判断修正分别标记；排版、翻译、迁移与例行复核不制造新消息。

今天、最近七天、自上次读完服务三种阅读节奏。阅读日期使用发现时间，真实发生时间另存。比如周日发现周五的官方修复：事件仍归属实际发生日期，但这次补录不能因为用户周六读完过简报而消失。因此，已读集合保存稳定变化 ID，而不是只保存一个时间水位。

打开页面不等于已读。收藏、关注和已读是三个独立状态；“已读完”只确认当前可见的阅读内容。资料截止时间使用 Asia/Shanghai，并标明 CST。没有今日更新就显示空状态，不能把旧快照包装成实时消息。

## 3. 证据是内容的一部分

事件首屏先给一句话事实、重要性、可用状态和主要外链。详细参数与六维评分放在次级区域。外链有可读标题和材料类型，可按看发布、实际使用、自行部署、验证效果、查看限制组织；缺少入口就留空，不为凑齐栏目补造链接。

官方公告能证明厂商发布了什么、声称了什么，不能自动证明性能或采用效果。补充来源也可能是官方文档或代码，不能一律称为二手材料。转载不算独立验证。

前沿观察允许公开研究与实验进入视野，但必须写明公开产物、已确认事实、未经验证的部分和下次观察条件。“工程精选”需要工程价值依据；只有同时存在可核查的关注度依据，才称为“低关注、高工程价值”。

## 4. 判断必须能延续，也能被修正

项目保存当前判断及其事件依据。趋势分别表达生命周期、置信度和近期活动；没有新消息不自动表示减弱。趋势与专题的证据区分支持、反对、背景，缺少反证记录也不等于不存在反证。

建议改变或判断纠正时，保存旧判断、新判断、原因与证据，而不是从最新快照倒推过去。专题围绕长期问题维护当前回答、适用边界、开放问题与复核条件。首批问题是：

- 开放权重模型能否承担 coding agent 工作流？
- 长时程 Agent 距离可靠运行还缺什么？
- MCP 企业采用的条件与限制是什么？

四个场景为构建 Agent、模型选型、本地部署、前沿研究。场景通过结构化关联影响排序和解释，不隐藏全局重大变化。ADOPT / TRIAL / WATCH 应面向具体人群、试用条件和限制，不能给出脱离语境的推荐。

## 5. 文件知识库与只读站点

保留 Astro、GitHub Pages、JSON / Markdown。项目、来源、专题、简报、复核任务分别存放；事件保留自己的证据与变化，避免多处重复维护事实。构建期生成页面数据、关系索引和搜索索引，浏览器不下载完整知识库。

阅读页是静态 HTML，搜索、筛选和个人状态使用客户端脚本。没有账号、数据库、在线模型调用或通知服务。本地偏好可导入、导出、清空，不自动跨设备同步；存储禁用或数据损坏时，核心阅读仍然可用，并提示状态未保存。

## 6. 生产闭环决定产品能否持续运行

每次扫描依次完成来源检查、候选筛选与去重、证据关联、事件和项目更新、到期复核、趋势和专题复核、双语报告与简报、持久化校验。固定 feed 和 API 提供稳定入口，全领域搜索负责发现和补漏。

预览、待开放权重、待独立验证等事项进入复核队列。优先采用官方承诺日期，否则默认发布后七天、三十天复核；每周检查最近三十天的重要遗漏。未检查、失败、无变化必须区分，成功访问页面也不等于核实内容。

所有必要阶段成功后，才由 `finalize-run.mjs` 最后原子更新 checkpoint。失败保留上次成功窗口，迁移和构建不推进 checkpoint。`last_updated_at` 仅表达实质变化，`last_reviewed_at` 表达复核，避免例行检查刷新未读或雷达活跃度。

## 7. 后续修改的验收问题

- 首页是否能用几分钟读完？操作是否有明确结果？
- 一个重要判断能否走到事件，再走到外部原文？
- 重跑、迟到补录和历史迁移会不会重复或漏掉变化？
- 手机和英文页面能否完成相同操作？
- 来源失败、未知和没有新消息是否被清楚区分？
